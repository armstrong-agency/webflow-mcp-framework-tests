# The Case for Client-First in Agent-Driven Webflow Development

(Advocate report, 2026-11-02. Scope of all claims: Webflow MCP beta v2.2.0, headless data tools, single-run probes, MCP read-back only — rendered DOM unverified. Every "today" means that surface, and the claim carries a stated expiry condition.)

## A. Steelman

**Core claim: Client-First is the only one of the three frameworks whose *entire intended workflow* runs through the part of the Webflow MCP that works — the class and variable surface — so it is the framework agents can build, verify, and recover with today.**

**1. The MCP has a reliable half and an unreliable half, and CF lives entirely in the reliable half.** The probes split the tool surface cleanly. Classes, combos, variables, element trees: all three frameworks' class mechanics passed. Components, slots, string Class props, custom properties, conditionals: blocked (plain elements in slots, nested slots), non-atomic (orphan sections on failed slot-name guesses, on both Lumos and Mast), unvalidated (nonexistent class accepted silently in a Classes prop), or silently corrupting (a calc()+var() expression rewritten on save, reported as success). Client-First's spec — custom `folder_element` classes, a short utility vocabulary, `is-` combos, rem sizing, variables — requires nothing from the unreliable half. Lumos's spec requires almost all of it: open components (any element in a slot — blocked), closed components (nested slot + `u-display-contents` — blocked headlessly), Trigger & State (custom properties rejected; one calc corrupted), Classes props (outside the style system). The current Mast starter is component-first too, so it inherits the same exposure. This is the honest framing: not "CF is better designed" but "CF's dependencies happen to be the subset of Webflow that the headless API does well."

**2. Cost per section, in tool calls.** A complete CF section — section_x > padding-global+padding-section-large > container-large > component div > heading/paragraph/button is-secondary — landed in one element-builder call with every class verified on read-back, because CF's canonical stacks ship pre-combined on the style guide (the probe sandbox is a blank Relume style guide). The MCP stores every multi-class stack as an ordered combo chain that must be created level-by-level before it can be applied, with a misleading "styles not found" error until it exists, and a different ordering is a different chain. CF's grammar sits at the cheap end of that tax: one custom class plus at most a known utility pair (0 extra calls when pre-existing, 3 when new). Mast's four-utility stack took 6 calls and failed outright when reordered. Lumos's custom-plus-up-to-four-utilities sits at the same expensive end. Multiply by every section of every page of every build.

**3. Auditability: everything an agent writes, it can read back.** The agent loop is write → read → verify. In CF, every styling decision is a class in the style system, so read-back is verification. Lumos and Mast "Class"/"Classes" string props render as raw class attributes the style tools cannot see or validate — the probe pushed a nonexistent class through one and it was accepted silently. For an unsupervised agent that is not a convenience gap, it is an audit hole: a category of state it can neither check nor repair. CF has no out-of-band channel by construction.

**4. Error recovery and graceful degradation.** CF's worst observed failure is the missing combo chain: recoverable with a two-line documented recipe, idempotent, no residue. The component path's worst failures are orphan partial sections left by non-atomic builds (reproduced on both Lumos and Mast), builder slot names that differ from the reported prop names on both starters, and the silent calc rewrite — a failure the agent cannot even detect without read-back diffing. When the MCP misbehaves, CF degrades to retryable errors; the component path degrades to cleanup jobs and corrupted styles.

**5. Training-data and ecosystem prior.** CF is plausibly the convention agents have seen most. Relume's library — 850+ components per [Webflow's own listing](https://webflow.com/libraries/detail/relume-library-lite), "built 100% in Client-First" — plus [Finsweet's free template series](https://webflow.com/website/fs-template-2) and years of cloneables mean CF markup saturates the public Webflow corpus; [Relume documents why it standardized on CF](https://relume.io/resources/docs/why-relume-uses-client-first), and agency writing calls it the de facto agency standard ([Agence Scroll](https://agence-scroll.com/en/blog/client-first-webflow-what-is-it) — one agency's claim, not survey data; say "arguably the most widespread," never "proven most popular"). Two concrete consequences: a model generating CF names is sampling from a distribution it has seen at scale, and [CF's own docs](https://finsweet.com/client-first/docs/intro) ban abbreviations and demand names "a Webflow developer, client, or any person" can read — which means an agent reading a site back gets self-documenting structure. CF was written so humans wouldn't need a decoder ring; agents are the newest beneficiary.

**6. Forward-compatible, not roadmap-dependent.** CF predates Webflow components and depends on none of them. Nothing stops wrapping CF sections in components later — Relume already ships CF-named components. Adopting CF today forecloses nothing when component and conditional APIs mature; adopting a component-first framework today means waiting for them.

**Where Emmett should NOT claim victory.** (a) Client no-code editing: Build Mode page slots, closed components, and variant dropdowns are genuinely better for editors than duplicated CF sections; Lumos's component strategy exists for that reason. (b) Cross-page content consistency: closed components solve a real problem CF solves only by discipline. (c) Theming: Lumos's variable-modes color system is elegantly designed and its variant-scoped modes passed via MCP first try. (d) Any claim about rendered output — the publish step was declined, so all evidence is MCP read-back. (e) Permanence — see B3. The honest headline: **"Client-First is the strongest framework for agent-built Webflow sites through today's MCP"**, not "Client-First is the best framework."

## B. Honest Rebuttals

**B1. "CF's open vocabulary means every custom class is a fresh naming decision — more variance and drift; Lumos/Mast components pre-decide the names."**
Response: CF constrains more than it looks. The section skeleton is fixed (page-wrapper > main-wrapper > section_x > padding-global+padding-section-* > container-*), the utility vocabulary is enumerated on the style guide, and custom names follow `folder_element`; the free choice is mostly the folder token. Lumos custom classes (`type_variation_element`) are exactly as open — the real contrast is only with pre-built component instances. And agents mitigate drift cheaply: read the style panel first, prefer existing classes, keep a naming skill. Concession: across long multi-session agent work without a read-first discipline, CF accumulates more naming decisions than instantiating Mast/Lumos components, and drift is a real failure mode worth testing (Test 3).

**B2. "CF produces more classes and more unused-class debt."**
Response: CF's debt is *visible* debt — every class lives in the style system, is countable, and Finsweet's extension cleans unused ones. Lumos/Mast Classes-prop usage creates the opposite: class references invisible to style tooling, which no cleanup tool can even enumerate. Measurable debt beats unmeasurable debt for any audited codebase. Concession: yes, a CF site carries more named classes and typically more CSS than a tight utility system; if the metric is stylesheet minimalism, CF loses it.

**B3. "The probes mostly indict the MCP's component tooling, not Lumos/Mast naming — when Webflow ships component and conditional APIs, the argument expires."**
Response: concede the structure of this openly — it is the strongest counterargument, and pre-conceding it is armor. Three qualifications. First, agents are shipping sites now; "best on the API that exists" is the only operationally meaningful claim, and there is no announced date for conditional or richer component APIs — the MCP server itself confirmed conditionals have no tool surface at all. Second, not everything expires: Classes props sit outside the style system *by framework design*, not MCP omission — an API can expose them but cannot make them auditable by style tools; and non-atomic multi-step component assembly is a transaction-model problem any API inherits until Webflow makes builds atomic. Third, the claim should be published *with* its expiry condition ("this flips when Webflow ships X, Y, Z") — that converts a rebuttal into a falsifiable prediction, which reads as rigor, not weakness.

**B4. "CF's duplicate-section style is exactly what conditionals and components exist to eliminate; betting on CF is betting against Webflow's roadmap."**
Response: the roadmap currently has no on-ramp for agents. Conditionals are Designer-only; the one visibility mechanism that works headlessly (boolean prop binding) is the very pattern Webflow's docs describe conditionals as superseding ("without needing additional 'visibility' props or duplicate elements"). So today the component-first frameworks are stranded between a deprecated pattern the API supports and a successor it doesn't expose — and an agent calling set_visibility may silently destroy an existing conditional (untested; see Test 5). CF isn't a bet against the roadmap, it's a position that composes with it: CF is a naming grammar, components are a packaging layer, and Relume proves they stack. Concession: the direction of Webflow's travel clearly favors conditional-driven components, and a CF-only shop should plan the migration, not deny it.

## C. Strawman Audit

**Arguments FOR CF that Emmett must not make:**
1. *"Cryptic abbreviations confuse AI."* No probe failure traced to a name. `u-mb-sm` resolved exactly as reliably as `margin-bottom`. The readability advantage, if real, is about comprehension and generation priors — assert it only with Test 4 data.
2. *"Lumos conditional visibility doesn't work via MCP."* Boolean prop→visibility binding passed first try, as did variant switching, variant-scoped variable modes, and authoring a component with a slot. The true claim is narrower: rule-based *Conditionals* have no API, and the binding that works is the superseded pattern.
3. *Conflating "the MCP is bad at components" with "component frameworks are bad."* The probe notes say it outright: orphan builds and slot-name mismatches are "component-system issues, not naming issues," reproduced identically on Mast and Lumos. Attack the dependency, never the design.
4. *"CF builds a section in one call; Lumos can't build sections."* Lumos assembled a full section via nested slots in one builder call — it took 3 attempts over slot names and left partial sections on the misses. The defensible contrast is zero-retry predictability and atomic failure, not capability.
5. *"CF is immune to the combo-chain problem."* CF-2b hit the same "styles not found" wall. CF hits it *less* (shallow stacks, pre-made pairs); it is a difference of degree.
6. *"CF is the proven most-popular standard."* No survey data exists, and Webflow's template marketplace doesn't even accept CF-named submissions ([open wishlist request](https://wishlist.webflow.com/ideas/WEBFLOW-I-6177)). Lead with Relume's 850+ CF components instead — concrete and checkable.
7. Anything resting on L-9c-style corruption as a *Lumos naming* flaw — it's a style-tool bug that happens to land on Lumos's Trigger/State system.

**Weak arguments AGAINST CF to knock down for credibility:**
1. *"CF is verbose; professionals use terse utilities."* Verbosity is the point: for a model reading an element tree back, `padding-section-large` is self-documenting where a terse token needs framework knowledge.
2. *"CF can't do theming or dark mode."* CF 2.x's variables guidance (primitives + semantic collections, dark mode on semantics) handles it; less automated than Lumos modes, not absent.
3. *"CF is obsolete because components exist."* They compose; Relume ships CF-named components, and CF sections wrap into components without renaming anything.
4. *"CF causes specificity hell."* One flat custom class plus scoped `is-` combos is a deliberately low-specificity design; the probes showed combos stay scoped to their base (`.probe_component.is-secondary` never collided with `.button.is-secondary`).

## D. Tests

**T1 (priority — supports A's core). Repeated scripted build trial.**
Hypothesis: an agent builds the same brief in CF with fewer tool calls, fewer retries, and no orphan state vs Mast and Lumos. Method: one fixed 5-section brief (hero, feature grid, testimonial, CTA, footer); N=10 scripted agent runs per framework on its own starter, fresh page each run, full cleanup between; log calls, errors, retries, orphan elements remaining, and read-back fidelity vs a per-framework intent spec. Metrics: median calls/section, retry rate, orphan count, fidelity %. Pass: CF median calls and retries strictly lowest AND zero orphans, with ≥95% fidelity. Cost: 1–2 days to script, ~30 agent runs of API spend; fully headless.

**T2 (closes the biggest evidence gap). Rendered-DOM verification.**
Hypothesis: MCP read-back "passes" correspond to correct published output — including confirming the L-9c corruption renders broken (opacity 0 in off state). Method: re-run the passing probes plus L-9c, publish each probe page to webflow.io, diff rendered DOM/CSS against intent. Metric: % of read-back passes confirmed in DOM. Pass: ≥95% confirmation and L-9c confirmed broken in render. Cost: hours; needs publish permission only.

**T3 (answers B1). Naming-drift trial.**
Hypothesis: CF naming variance across independent agent sessions is no worse than Lumos custom-class variance. Method: 10 independent sessions per framework, each told to name classes for the same 3 novel components given only the starter's existing style read-back; no shared memory. Metrics: distinct-name count per intended role, collisions with existing site classes, spec-conformance (CF folder_element / Lumos type_element rules). Pass: CF's distinct-name spread ≤ Lumos's and zero collisions. Cost: ~60 short sessions, half a day scripted.

**T4 (tests the comprehension claim before anyone asserts it). Same-DOM quiz.**
Hypothesis: a model answers structural questions more accurately from CF markup. Method: build one identical page per convention (T1 output), hand each DOM + style read-back to a model with no framework docs, ask 15 fixed questions (which element carries section padding? what does `is-featured`/`cc-active` modify? where would you change all buttons site-wide?); blind-score across 3 model families. Metric: accuracy per convention. Pass: CF ≥ both others by a margin exceeding run-to-run noise. Cost: hours once T1 pages exist.

**T5 (supports B4; already designed in conditionals.md). Conditional survival.**
Hypothesis: an MCP set_visibility call destroys or orphans an existing Designer-authored conditional. Method: 2 minutes of Designer work to add one visibility conditional; then get_settings (is it readable?), set_visibility static true (does it survive?), publish and check DOM. Pass for the CF case: conditional unreadable or destroyed. Cost: minutes; the one test needing manual Designer steps.
